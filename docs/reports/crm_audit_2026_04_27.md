# CRM Module Audit - 2026-04-27

Scope: `/crm`, `/crm/leads`, `/crm/customers`, CRM server actions, validation, loading time, chunk performance, and security boundaries.

## Summary
- Critical issues: 4
- Warnings: 6
- Suggestions: 4
- Verification: targeted `eslint`, `tsc --noEmit`, `perf:audit`, and `perf:chunks` passed.
- Current chunk status: no app route over 80KB. `/crm/customers/page` is 37.1KB; `/crm/leads/page` is 0.5KB app-route chunk, with heavier Kanban loaded dynamically.
- Release recommendation: do not treat CRM as production-safe until the P0 data-integrity and RBAC bypass issues below are fixed.

## Critical Issues

1. Lead assignment and status rules can be bypassed through full create/update actions
   - Files: `app/actions/lead-actions.ts:90`, `app/actions/lead-actions.ts:152`, `app/actions/lead-actions.ts:173`, `app/actions/lead-actions.ts:175`, `lib/validations/crm.schema.ts:69`
   - Current behavior: `createLead` and `updateLead` accept `assigned_to` and `status` through the full payload after only `requireCrmAccess`.
   - Impact: a `sale` user can bypass the stricter `assignLead` self-assign policy and can directly set status without the `VALID_LEAD_TRANSITIONS` state machine.
   - Required fix: remove `status` and `assigned_to` from general update payload, or enforce the same RBAC/transition checks used by `assignLead` and `moveLeadToStage`.

2. Customer phone dedup silently overwrites existing customer data
   - File: `app/actions/customer-actions.ts:123`
   - Current behavior: creating a customer with an existing phone updates the old customer and sets many omitted fields to `null` or `[]`.
   - Impact: a duplicate-phone create can erase existing email, address, notes, tags, wedding fields, and source without the user realizing they are editing an old record.
   - Required fix: either return a duplicate warning and open the existing record, or merge only non-empty fields with explicit user confirmation.

3. Lead financial/score validation is incomplete on create and full update
   - Files: `lib/validations/crm.schema.ts:75`, `lib/validations/crm.schema.ts:77`, `app/actions/lead-actions.ts:118`, `app/actions/lead-actions.ts:173`
   - Current behavior: quick actions validate `dealValue >= 0` and `score 0..100`, but `ZodLeadCreate` and `ZodLeadUpdate` do not.
   - Impact: direct server action calls can persist negative deal values or invalid scores, breaking funnel quality and analytics.
   - Required fix: apply `.min(0)` to `deal_value` and `.min(0).max(100)` to `score` in the create schema that update extends.

4. CRM RPC release/security boundary is not fully captured in migrations
   - Files: `app/actions/lead-lifecycle.ts:228`, `app/actions/lead-lifecycle.ts:270`, `app/actions/customer-actions.ts:159`, `supabase/migrations/20260409034800_crm_lead_stats_rpc.sql:7`
   - Current behavior: code depends on `convert_lead_to_customer`, `append_care_log`, and `nextval_customer_code`, but the executable migration definitions are not present under `supabase/migrations` except for lead stats. `get_crm_lead_stats` is also `SECURITY DEFINER` and granted to all authenticated users.
   - Impact: a clean production migration can miss required CRM RPCs. Also, non-CRM authenticated roles may call the stats RPC directly and read aggregate CRM counts unless DB privileges/RLS elsewhere block it.
   - Required fix: add/verify migrations for the missing RPCs; revoke broad RPC grants or add role checks inside SECURITY DEFINER functions.

## Warnings

1. Lead funnel/source widgets calculate from the current page, not the full dataset
   - Files: `components/crm/lead-list-page.tsx:239`, `components/crm/widgets/widget-sales-funnel.tsx:13`, `components/crm/widgets/widget-source-donut.tsx:12`
   - Impact: with pagination over 50 leads, analytics cards can show misleading funnel/source numbers.

2. Customer LTV and stats include all matching contracts without `deleted_at` filtering
   - Files: `app/actions/customer-actions.ts:79`, `app/actions/customer-actions.ts:104`, `app/actions/customer-actions.ts:300`
   - Impact: deleted or cancelled contracts can inflate LTV. `getCustomerStats` also loads all contract rows, which is a time-load risk as contracts grow.

3. Pagination inputs are not capped
   - Files: `lib/validations/crm.schema.ts:45`, `lib/validations/crm.schema.ts:51`, `app/actions/lead-actions.ts:62`, `app/actions/customer-actions.ts:56`
   - Impact: direct server action calls can request very large pages and create avoidable DB/app pressure.

4. Care log storage and UI parser are mismatched
   - Files: `app/actions/lead-lifecycle.ts:270`, `components/crm/lead-care-log.tsx:65`
   - Current behavior: RPC appends JSON text lines, while the UI splits text by newline and parses `[tag] message` style text.
   - Impact: care history can display as raw JSON instead of a structured timeline.

5. Convert lead audit assumes a newly-created customer
   - File: `app/actions/lead-lifecycle.ts:241`
   - Impact: the RPC may link to an existing customer by phone, but the audit log always writes `CREATE customers`, making audit history inaccurate.

6. Customer detail hides contract query errors
   - File: `app/actions/customer-actions.ts:104`
   - Impact: the drawer can show customer info with empty contracts/LTV if the contract query fails, instead of surfacing a partial-load error.

## Positive Findings

- CRM server actions consistently use `withAuth` plus `requireCrmAccess`.
- Delete actions are soft-delete and restricted to admin/manager.
- `assignLead` has sale self-assign protection.
- Lead stats moved to an RPC instead of client-side full-table counting.
- Kanban board is dynamically imported, keeping route chunks below budget.
- Targeted lint, TypeScript, `perf:audit`, and `perf:chunks` pass.

## Suggested Fix Order

1. P0: harden `createLead/updateLead` field-level RBAC and transition enforcement.
2. P0: change customer duplicate-phone behavior to non-destructive duplicate handling.
3. P0: add schema range constraints and page-size caps.
4. P1: add/verify CRM RPC migrations and tighten RPC grants.
5. P1: move CRM analytics widgets to server/RPC-backed totals, not current-page data.
6. P1: filter deleted contracts from LTV and replace full contract scans with aggregate RPC.
7. P2: normalize care log storage/rendering.
